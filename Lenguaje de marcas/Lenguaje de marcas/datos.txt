1. ESTRUCTURA GENERAL DEL PROYECTO
Para comenzar este trabajo, he decidido plantear una estructura base que se repite en todas las páginas para mantener la coherencia visual. En lugar del clásico menú superior, he implementado un menú lateral izquierdo usando la etiqueta semántica <aside> con la clase ".barra-lateral". Dentro de este bloque he colocado el título de la empresa y el menú de navegación (<nav>) con sus respectivos enlaces (<a>) que conectan todas las páginas entre sí, tal y como pide el enunciado.

El contenido principal de cada página lo he metido dentro de una etiqueta <main> con la clase ".area-contenido".
A nivel de CSS general, he empezado haciendo un reseteo universal con el selector "*" para quitar márgenes y paddings que traen los navegadores por defecto. También he declarado variables en la pseudo-clase ":root" para los colores, eligiendo un tema oscuro (Dark Theme) con tonos grises oscuros, cian y magenta, ya que le da un aspecto muy tecnológico y de ciberseguridad, ideal para nuestra rama de ASIR. Para que el menú lateral y el contenido principal se coloquen correctamente uno al lado del otro, he aplicado "display: flex" a la etiqueta <body>.

Adicionalmente, en todas las páginas se incluyen tres elementos globales comunes:
- Dos <div> para el cursor personalizado (#cursor-ring y #cursor-dot), controlados por JS.
- Un <div class="scan-line"> que genera la línea de escaneo animada mediante CSS.
- Un <div id="toast"> que actúa como sistema de notificaciones, activado mediante JS.
- Un bloque <div class="sidebar-footer"> al pie del menú lateral con la versión del sistema.

- HTML: He insertado una imagen principal usando la etiqueta <img>. Debajo, he utilizado un contenedor <section class="caja-destacada"> para dar la bienvenida al usuario. 6. JAVASCRIPT (js/main.js)
He integrado un archivo JavaScript externo vinculado al final del <body> de todas las páginas mediante <script src="js/main.js">. Este archivo implementa los siguientes módulos, todos encapsulados en IIFEs (Immediately Invoked Function Expressions) para no contaminar el ámbito global:

- initCursor(): Captura el evento "mousemove" y coloca el punto magenta (#cursor-dot) de forma instantánea. El anillo cian (#cursor-ring) sigue al ratón con un lag suavizado mediante "requestAnimationFrame" e interpolación lineal (factor 0.12). Al hacer clic, el anillo se escala al 75% y vuelve al 100% al soltar, dando un feedback visual. Al salir del viewport se ocultan ambos elementos con "opacity: 0".

- setActiveNav(): Compara el nombre del archivo actual (obtenido de "window.location.pathname") con el "href" de cada enlace del menú, añadiendo la clase "activo" al enlace correspondiente. Esto resalta visualmente la página en la que está el usuario sin duplicar código en cada HTML.

- initCounters(): Observa con "IntersectionObserver" los elementos ".stat-numero[data-target]". Cuando un contador entra en pantalla, lanza un intervalo que incrementa el número desde 0 hasta el valor indicado en "data-target" en 1800 ms, concatenando el sufijo definido en "data-suffix". Esto evita que la animación se ejecute antes de que el usuario vea el elemento.

- initUptimeBars(): Observa con "IntersectionObserver" los elementos ".uptime-fill[data-width]". Al entrar en pantalla, asigna el ancho del atributo "data-width" como propiedad "style.width", lo que dispara la transición CSS "@keyframes loadBar" que anima la barra de izquierda a derecha.

- mostrarToast() + initForm(): La función "mostrarToast()" añade la clase "show" al elemento "#toast" (haciéndolo visible con una transición CSS) y la elimina 3,5 segundos después. "initForm()" intercepta el evento "submit" del formulario con "preventDefault()" para evitar el envío real y llama a "mostrarToast()" con el nombre del usuario. También captura el evento "reset" para informar de que el formulario ha sido limpiado.

- initTyped(): Lee el elemento con el atributo "data-typed" (que contiene un JSON de frases), y simula el efecto de máquina de escribir: escribe letra a letra, hace una pausa al terminar cada frase y borra letra a letra antes de pasar a la siguiente. La velocidad de escritura y la pausa son configurables mediante los atributos "data-typed-speed" y "data-typed-pause".

- initGlitch(): Copia automáticamente el "textContent" de cada elemento con la clase ".glitch" al atributo "data-text" si este no estaba definido en el HTML. Esto es necesario para que los pseudo-elementos CSS "::before" y "::after" del efecto glitch puedan leer el texto con "content: attr(data-text)".

- initClickParticle(): En cada clic del usuario genera 6 partículas circulares de colores cian, magenta y verde que se dispersan en abanico desde el punto de clic y desaparecen en 650 ms, usando transiciones CSS y "requestAnimationFrame" para el render inicial.

8. APARTADO XML, XSD Y XSLT (carpeta /xml)
Para la parte del Proyecto Intermodular, aparte de la web corporativa, he añadido una carpeta llamada "xml" donde he desarrollado la gestión de información estructurada que también pide el módulo 0373. Como MoGarry es una empresa de infraestructura y datacenter, me ha parecido lógico que la información que tenga que representar sea el inventario de los equipos físicos del centro de datos. Así además los equipos coinciden con los modelos que ya aparecen en la página de infraestructura y todo queda conectado.

He estructurado el XML (datos.xml) en tres bloques jerárquicos. El primero es <empresa>, donde van los datos generales como el CIF, la fecha del inventario y el responsable. El segundo es <salas>, con las tres salas del datacenter (Producción, Backup y SOC), cada una con su capacidad de rack en unidades U, su temperatura objetivo y su certificación Tier. El tercero es <equipos>, donde he metido diez equipos representativos: dos servidores HPE ProLiant, un switch Cisco Nexus, un router Cisco ASR, dos firewalls (Palo Alto y Fortinet), dos NAS NetApp, un SAI APC y un servidor antiguo en mantenimiento. Cada equipo lleva su fabricante, modelo, número de serie, ubicación física dentro del datacenter (sala, rack y unidad), datos de red (IP, MAC y VLAN si tiene), fechas de compra y fin de garantía, y los servicios que presta.

Para vincular cada equipo con la sala donde está físicamente, he utilizado xs:ID en el atributo "id" de cada sala y xs:IDREF en el atributo "sala" de la ubicación del equipo. Esto hace que el validador compruebe automáticamente que ningún equipo apunte a una sala que no exista, lo cual a nivel XML sería el equivalente a una clave foránea en una base de datos.

El esquema de validación (esquema.xsd) tiene 11 tipos simples y 6 tipos complejos. He intentado que no sea un XSD de adorno, sino que valide de verdad, así que incluye:
- Tipos de datos correctos: xs:date para las fechas, xs:positiveInteger para las capacidades, xs:decimal con un decimal para las temperaturas.
- Patrones (xs:pattern) para el CIF (letra inicial seguida de 8 dígitos), IPv4 con octetos válidos de 0 a 255, MAC hexadecimal de 6 grupos, número de serie con formato corporativo (FABRICANTE-MODELO-AÑO-NUM), código de rack (R-XX) y unidad de rack (U seguido de dos dígitos).
- Enumeraciones para los tipos de equipo (servidor, switch, router, firewall, nas y sai), los estados (operativo, mantenimiento, baja y almacen) y las certificaciones del datacenter (Tier I a Tier IV).
- Rangos numéricos para la VLAN (entre 1 y 4094) y para la temperatura (entre 15.0 y 30.0 grados).
- Cardinalidades con minOccurs y maxOccurs: mínimo una sala, mínimo un servicio por equipo, máximo diez servicios.

Para demostrar que el XSD detecta los errores correctamente, he creado un archivo aparte llamado "datos-invalido.xml" donde he metido siete fallos a propósito: un CIF sin la letra inicial, un tipo de equipo "impresora" que no está en la enumeración, un estado "encendido" que tampoco existe, una IP imposible (999.999.1.1), una MAC con caracteres no hexadecimales (ZZ:1A:2B...), una VLAN fuera del rango (9999) y una referencia a una sala que no existe (SALA-Z). En la carpeta "capturas" están guardadas las dos pruebas en VSCode: en "valida-ok.png" se ve el datos.xml correcto sin errores, y en "valida-fallo.png" se ve el datos-invalido.xml con todos los errores subrayados en rojo y listados en el panel de Problemas. También he dejado un archivo de texto "evidencia-validacion.txt" con la salida de la validación ejecutada desde terminal con la herramienta xmllint, por si se quiere ver también en formato texto.

Como ampliación, he hecho también una hoja de estilos XSLT (inventario.xsl) que transforma el datos.xml en una página HTML con el mismo estilo dark cyber de la web corporativa (cian, magenta y fondo oscuro). En la segunda línea del datos.xml he añadido la línea <?xml-stylesheet type="text/xsl" href="inventario.xsl"?> que es la que le indica al navegador que aplique la transformación. De esta forma, en vez de ver el XML como un árbol de etiquetas plegables, al abrirlo con Live Server se ve un panel de gestión con las tres salas como tarjetas y una tabla con los diez equipos. Los estados se muestran con badges de colores: verde para "operativo", naranja para "mantenimiento" y gris para "almacen". El resultado se puede ver en la captura "inventario-renderizado.png". Para la lógica del XSLT he usado xsl:template, xsl:for-each para recorrer las salas y los equipos, xsl:value-of para extraer el contenido de cada nodo, xsl:choose con xsl:when para mostrar un guión cuando un equipo no tiene IP (por ejemplo el SAI), y xsl:attribute para asignar dinámicamente la clase del badge según el estado.

Un detalle importante: la transformación XSLT no funciona en Chrome ni en Edge cuando se abre el archivo directamente como "file://" por motivos de seguridad. Para que se vea bien hay que servirlo por HTTP (yo lo he probado con Live Server de VSCode, que abre el archivo en "http://127.0.0.1:5500/xml/datos.xml") o abrirlo directamente con Firefox, que sí lo permite.

Sobre cómo encaja este apartado en el resto del Proyecto Intermodular: este XML representa lo que en realidad sería una exportación del inventario que viviría en la base de datos del módulo 0372, donde habría dos tablas equivalentes "salas" y "equipos". Encaja también con el módulo 0370 (Redes) porque los equipos del XML son los mismos que aparecen en la topología de Cisco Packet Tracer, y con el 0371 (Hardware) porque los modelos que he elegido (HPE ProLiant, Cisco Nexus, NetApp AFF, Palo Alto, Fortinet, APC) son los que se justifican en la documentación de la infraestructura física.
